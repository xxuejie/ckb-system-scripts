# fuzzing

This directory contains a fuzzing setup for ckb-system-scripts. For the moment only fuzzers for the multisig script have been prepared, but it should be trivial to add fuzzers for others.

## Overfiew

Our fuzzing setup relies on [ckb-vm-syscall-tracer](https://github.com/xxuejie/ckb-standalone-debugger/tree/tracer/ckb-vm-syscall-tracer) to work. `ckb-vm-syscall-tracer` executes a script given a [MockTransaction](https://docs.rs/ckb-mock-tx-types/latest/ckb_mock_tx_types/struct.MockTransaction.html), it then records the input / output data for each syscall, the syscall data are then gathered in a [protobuf](https://github.com/xxuejie/ckb-standalone-debugger/blob/tracer/ckb-vm-syscall-tracer/protos/traces.proto) formatted structure. The gathered data then serve 2 purposes:

* They can be fed into [mock syscalls](https://github.com/xxuejie/ckb-script-fuzzing-toolkit/blob/main/mock_syscalls/fuzzing_syscalls.cc) for CKB script code to run outside of CKB-VM environment.
* They can serve as corpus used by fuzzing engines.

Our fuzzing setup embraces [structure aware fuzzing](https://github.com/google/fuzzing/blob/master/docs/structure-aware-fuzzing.md) from the beginning, it leverages the handy [libprotobuf-mutator](https://github.com/google/libprotobuf-mutator) to mutate protobuf structures in an effective way. This is also the reason why recorded syscalls are serialized into protobuf format, not molecule format.

As a result, a unified workflow can be used iby most CKB script repositories to introduce fuzzing setup:

* Rely on existing unit tests to dump executable CKB transactions in `MockTransaction` format.
* Use `ckb-vm-syscall-tracer` to run each `MockTransaction`, then record syscall data as corpus.
* Reuse current CKB script implementation, but swap RISC-V syscalls with [mock syscalls](https://github.com/xxuejie/ckb-script-fuzzing-toolkit/tree/main/mock_syscalls) to build usable fuzzers. Sanitizers and fuzzing setup from each fuzzing engine might also be leveraged in this step. Notice for now, the generated fuzzers are x64 native binaries(or arm64 binaries), not RISC-V binaries.
* Finally, start a fuzzer with generated corpus, monitor for potential broken assertations.

This directory serves as an example of introducing fuzzing to a CKB script repository, following the above workflow.

## Design Choices

Certain design choices are made in the fuzzing workflow:

* Unless absolutely necessary, we will focus on CKB-VM starting fro script version V2. Meaning spawn will be first-class citizens.
* Dynamic linking is not supported in the fuzzing workflow. This is a deliberate choice, when spawn is available, dynamic linking should be deprecated.

## Basic Usage

All dependencies for fuzzer have been packed in a [docker image](https://hub.docker.com/r/xxuejie/ckb-script-fuzzing-toolkit), ideally one only needs `make` and `docker` install to play with the fuzzers.

To get started, we need to clone and build system scripts first:

```bash
$ git clone https://github.com/xxuejie/ckb-system-scripts
$ cd ckb-system-scripts
$ git checkout fuzzing
$ git submodule update --init
$ make all-via-docker
```

To play with fuzzers, we can use the fuzzer repl:

```bash
$ make -C fuzzing repl
root@6b22a31f5e77:/code#
```

In case you are using a limited network environment, you can tweak proxy settings:

```bash
$ make -C fuzzing repl DOCKER_RUN_ARGS="-e ALL_PROXY=$ALL_PROXY -e HTTP_PROXY=$HTTP_PROXY -e HTTPS_PROXY=$HTTPS_PROXY"
root@6b22a31f5e77:/code#
```

This is a playground you can use, for example, you can generate corpus from existing unit tests:

```bash
root@6b22a31f5e77:/code# make -C fuzzing prepare
```

Note each run of `make -C fuzzing prepare` will remove previously generated corpus, and regenerate new corpus from scratch. It does not matter if you have previously run this command or not, new corpus will always be generated.

You can build all fuzzers:

```bash
root@6b22a31f5e77:/code# make -C fuzzing build
```

Or you can combine the 2:

```bash
root@6b22a31f5e77:/code# make -C fuzzing
```

Which will first run `prepare` task, then `build` task.

Current fuzzing setup support 3 fuzzing engines:

* [LLVM's libfuzzer](https://llvm.org/docs/LibFuzzer.html)
* [honggfuzz](https://honggfuzz.dev/)
* [AFL++](https://aflplus.plus/)

We can try them one by one.

### LLVM libfuzzer

Let's first copy multisig corpus to a new folder:

```bash
root@6b22a31f5e77:/code# cp -r fuzzing/corpus/multisig fuzzing/corpus_multisig_llvm
```

This step is optional, but in case you want to try different fuzzers, using separate folders help you maintain corpuses generated by different fuzzers.

Now we can run the LLVM libfuzzer:

```bash
root@6b22a31f5e77:/code# ./fuzzing/multisig_llvm_fuzzer fuzzing/corpus_multisig_llvm
```

You will notice outputs generated by LLVM libfuzzer. It's also possible to run mulitple jobs to utilize more cores:

```bash
root@6b22a31f5e77:/code# ./fuzzing/multisig_llvm_fuzzer fuzzing/corpus_multisig_llvm -jobs=4
```

A fuzzer typically runs indefinitely unless it finds a problem, so if the fuzzer does not stop, you can use `Ctrl + c` to terminate it.

### Honggfuzz

Similarly, let's also create a folder just for honggfuzz corpus:

```bash
root@6b22a31f5e77:/code# cp -r fuzzing/corpus/multisig fuzzing/corpus_multisig_honggfuzz
```

And we can run honggfuzz:

```bash
root@6b22a31f5e77:/code# honggfuzz -i fuzzing/corpus_multisig_honggfuzz -- fuzzing/multisig_honggfuzz_fuzzer ___FILE___
```

By default honggfuzz will use half the CPU cores, so there might not be a need to set the multiple jobs.

Similar to LLVM libfuzzer, use `Ctrl + c` to terminate honggfuzz.

### AFL++

Let's also create a folder just for AFL++:

```bash
root@6b22a31f5e77:/code# cp -r fuzzing/corpus/multisig fuzzing/corpus_multisig_aflxx
```

And we can run AFL++, one more note is that AFL++ separates input corpus from output corpus, so 2 folders are needed:

```bash
root@6b22a31f5e77:/code# afl-fuzz -i fuzzing/corpus_multisig_aflxx -o fuzzing/corpus_multisig_aflxx_o -- fuzzing/multisig_aflxx_fuzzer @@
```

## Optional Features

There are also optional features that you can choose to use in the fuzzing setup:

### Text proto format

By default, the protobuf structure containing syscall input / output data will be serialized in binary format. However, some fuzzing engines might be better suited for protobuf messages in [text format](https://protobuf.dev/reference/protobuf/textformat-spec/). This can be enabled.

If you have previously build the fuzzers, clean them first:

```bash
root@6b22a31f5e77:/code# make -C fuzzing clean
```

Now you can build fuzzers using text formats(since `clean` would clean up corpus as well, let's also build corpus here):

```bash
root@6b22a31f5e77:/code# make -C fuzzing USE_TEXT_PROTO=true
```

Text based corpuses will be kept in `fuzzing/corpus_text` folder. Make sure to use those corpuses, while it is fine using binary corpuses for text based fuzzers theoretically, it is not an efficient way of fuzzing:

```bash
root@6b22a31f5e77:/code# cp -r fuzzing/corpus_text/multisig fuzzing/corpus_multisig_llvm_text
root@6b22a31f5e77:/code# ./fuzzing/multisig_llvm_fuzzer fuzzing/corpus_multisig_llvm_text
```

### Embed secp256k1 data

While some of our latest CKB scripts get rid of secp256k1 precomputed table by tweaking `ecmult-window` config, the system scripts included in this repo can only function in the presence of precomputed tables. This means our fuzzing script will rely on CKB syscalls to load 1MB of precomputed data. All of those data will go into the corpus, brining a huge pressure on fuzzing engines.

To cope with this issue, our fuzzing setup for the system scripts implements a new mode, where the secp256k1 precomputed tables will be bundled in each compiled program, so they are not loaded by syscalls anymore. This way corpus will be much, much smaller, fuzzing engines can tweak them for better code coverage.

If you are still inside the docker container, exit it first:

```bash
root@6b22a31f5e77:/code# exit
```

Let's clean everything to avoid any potential confusion:

```bash
$ sudo make clean
$ make -C fuzzing clean
```

We need to rebuild the system scripts with secp256k1 precomputed tables included:

```bash
$ make all-via-docker FUZZING_EMBED_DATA=true
$ ls -lh specs/cells
total 3.2M
-rwxr-xr-x 1 root root 7.8K Apr  9 05:26 dao
-rwxr-xr-x 1 root root 1.1M Apr  9 05:26 secp256k1_blake160_multisig_all
-rwxr-xr-x 1 root root 1.1M Apr  9 05:26 secp256k1_blake160_sighash_all
-rw-r--r-- 1 root root 1.0M Apr  9 05:26 secp256k1_data
```

By checking the size of multisig script, we can verify that the precomputed table is indeed bundled inside the binary.

Let's fire up fuzzer repl and rebuild everything with embed mode enabled:

```
make -C fuzzing repl
root@310eb067b52d:/code# make -C fuzzing FUZZING_EMBED_DATA=true
```

If you dive into the full logs, you will notice one unit test failure(because cycle consumptions are different), we can safely ignore it, the corpus will still be useful even though some tests fail. In fact, the unit tests do generate a lot of corpuses which will lead to CKB script validation failure(a non-zero return code will be returned). For now the fuzzers only worry about sanitizers and assertions. We might reach the point where we care and can use return code in the future.

Now we can rerun one of the same fuzzers:

```bash
root@310eb067b52d:/code# cp -r fuzzing/corpus/multisig fuzzing/corpus_multisig_honggfuzz
root@310eb067b52d:/code# honggfuzz -i fuzzing/corpus_multisig_honggfuzz -- fuzzing/multisig_honggfuzz_fuzzer ___FILE___
```

You might notice from fuzzer coverage reports, that more code can be covered in shorted time, this is due to the fact that fuzzers don't have to tweak that giant precomputed table anymore, and can quickly explore more directions.

Still, in some cases one might still want to fuzz with the giant precomputed table as part of the corpuses. It really depends on individual scenario to decide if this feature should be turned on or off.
